# コンテスト仕様

## 作成と公開範囲

- `/contests/new` から `contest_organizer` または `admin` が作成します。編集は主催者・管理者のみです。凍結中のユーザーの参加・提出・更新は拒否します。
- タイトル、ASCIIの識別名、Markdown説明、開始・終了日時、ペナルティ、順位表の公開範囲、Rated、問題セットを設定します。日時入力は日本時間（UTC+09:00）です。
- 問題セットは1〜100問。問題ごとに一意のラベル・整数配点（1〜1,000,000）・順序を指定します。公開問題または編集者が所有する問題を選択できます。配点は合計100点である必要はありません。
- 開催期間は正の長さで最大31日。開始を含み、終了を含みません。開始後は開催期間・問題セット・配点・ペナルティ・Rated設定を固定します。タイトル・説明・順位表設定は編集できます。
- `public` は一覧掲載、`unlisted` は直接リンクで閲覧・参加、`private` は主催者・管理者のみです。privateへの一般利用者の招待機能はありません。
- 開催前の問題名・リンクは主催者・管理者以外に公開しません。開催中・終了後は、閲覧可能なコンテストのリンクからセット内の非公開問題も閲覧できます。通常の非公開問題URLは引き続き制限します。
- 正式提出は開催中のみ。未参加の場合は有効な提出受付時に自動参加します。終了後の通常提出は練習扱いで、正式順位表には含めません。

## 得点と順位表

- `コンテスト得点 = 問題得点（0〜100） × 満点配点 ÷ 100`。0〜100の範囲に制限し、小数第2位まで保持します。500点の問題で50点の部分点なら250点です。
- 各問題の最高得点を合計します。その最高点を最初に取得した提出の経過分を使用します。正の部分点にも到達時間を加算します。
- 満点に到達した問題のみ、最高点到達前の失敗提出数×設定ペナルティを加算します。CE・IE・取消は失敗回数に数えません。未完了・IE・取消の提出は得点に使いません。
- 合計点降順、ペナルティ昇順、最高得点の最終到達時刻昇順で順位を決めます。この3条件が同じなら同順位です。ユーザーIDは同順位内の表示順だけに使用します。
- `full` は全詳細、`partial` は終了まで合計のみ、`hidden` は終了まで順位表を非表示。終了後はいずれも詳細を公開します。
- 表示中は5秒間隔でAPIから更新します。非表示タブでは停止し、復帰時に再取得します。通信失敗時は最大30秒まで間隔を延ばします。WebSocket/SSEではありません。
- APIはケース・ソースコードを返さず、当該コンテストの判定状態をDBから更新します。得点集計とレーティング計算にはプロセス内キャッシュを使用します。

## バーチャル参加

- 終了した閲覧可能なコンテストで、ログインした利用者が開始できます。コンテスト・ユーザーごとに1回です。
- 開始日時はサーバーが確定し、本来の開催時間と同じ長さの個人タイマーをDBに保存します。同時に開始ボタンを押しても同じ参加ID・開始時刻を返します。
- 再読み込み・worker再起動でタイマーをリセットしません。期限または明示的な終了後は再開できません。
- 提出リンクにコンテストIDと個人参加IDを含めます。他人のID、別コンテストのID、期限外の提出は拒否します。
- 個人順位表にのみ加算し、正式順位表とレーティングには含めません。他人のバーチャル提出は管理者以外に公開しません。
- バーチャル参加IDがない終了後の提出は通常練習です。UIのタイマーは補助表示で、受付の可否はサーバー時刻で決定します。

## OJP Elo

- AtCoderとは独立した指標です。初期値1500、K=32。対象は主催者が開始前にRatedを有効にした公開コンテストだけです。既存のRated未設定コンテストはUnrated扱いです。
- 正式提出を行った対象者が2人以上必要です。主催者・セット内問題の出題者・参加登録だけの人・バーチャル参加・取消提出だけの人は対象外です。
- 相手に対する期待勝率は `1 / (1 + 10^((相手の旧rating - 自分の旧rating)/400))`。順位による実績は勝ち1、同順位0.5、負け0です。
- 全対戦相手の「実績−期待勝率」の平均に32を掛け、旧ratingに加算して整数へ丸めます。最小値0。同じ旧ratingの2人で明確な勝敗なら勝者1516、敗者1484です。
- イベント内では全員の更新前ratingを使用し、コンテスト終了時刻順に計算します。対象提出に未完了・IEがあれば、そのイベントと後続イベントの計算を保留します。対象外の提出や対象者2人未満のイベントは後続を止めません。
- 現在の提出データから履歴を決定的に再計算する方式です。再ジャッジで二重に加算しません。再ジャッジ・管理者による削除・非公開化で過去の結果が変われば後続の履歴も変わります。不変の公式rating確定台帳ではありません。
- 開始後の通常編集ではRatedの変更やRatedイベントの非公開化を拒否します。管理者のモデレーションによる非公開化・削除は可能です。
- `/ratings` にルール・全体順位表、`/me` に現在値と履歴、コンテスト終了後の順位表に増減を表示します。

## 保存と導入

コンテスト本体・参加登録・提出の参加種別は既存のAppState、判定はRuntime専用テーブル、バーチャルタイマーは `ContestVirtualParticipation` に保存します。ratingは派生データで、専用の保存テーブルはありません。

```bash
npm run db:generate
npm run db:contest
npm run build
```

`db:contest` は `prisma/contest-schema.sql` のテーブル・インデックス追加だけを適用します。本番では先にカスタム形式のDBバックアップと別DBでの復元確認を行ってください。全体の `db:push`、既存データの削除、追加のConfig Varsは不要です。

## 検証

```bash
npm run test:contest
npm run test:i18n
npm run lint
```

`test:contest:integration` は専用の `ojp_contest_test` DBと `http://127.0.0.1:3100` のweb、別の実workerを使います。通常は環境変数未設定でスキップし、DB名・接続先を検査して本番での実行を拒否します。テストは専用環境にダミー管理者・参加者、問題ZIP、コンテスト、提出を作成し、過去の同テスト用コンテストを削除するため、共有・本番DBは使用しないでください。

GitHub Actionsのcontestsジョブが専用PostgreSQLを作成して通しテストを実行します。ローカルでは `DATABASE_URL` と `CONTEST_TEST_DATABASE_URL` を同じ専用DBにし、`AUTH_SECRET=contest-local-validation-only-not-production`、`ADMIN_GITHUB_LOGINS=contest-test`、`STORE_DB_SYNC=1`、`LEARNING_STORAGE=db` を設定します。R2/OAuthの本番資格情報は渡しません。webは `JUDGE_PROCESS_MODE=web`、workerは `JUDGE_PROCESS_MODE=worker` で起動し、テスト実行時に `CONTEST_HTTP_TEST_ORIGIN=http://127.0.0.1:3100` を指定します。

2026-10-11の検証では、単体16件、専用DBの並列開始・永続化、WindowsとLinuxの実web/workerによる権限・採点・Elo・バーチャル・再ジャッジが成功しました。Linuxでは2台のworkerで確認しました。ブラウザで配点・並び順・日英切り替え、順位表の自動反映、再読み込み後の個人タイマー、スマートフォン幅を確認しました。終了確認はページ内表示にして、確認・キャンセル・確定・再読み込み後の終了状態までブラウザで検証しました。

## 残る基盤課題

- AppState全体のプロセス間の書き込み競合は、個別DB行への移行または全書き込み共通の版管理が必要です。今回の保存完了待ち・起動時読込待ちは完全な競合解消ではありません。
- ジョブ登録を提出ID単位で直列化し、再ジャッジ時の古い判定キャッシュを読み直します。ただし、実行世代・lease喪失後の結果書込み・ケース結果のDB一意制約を含むキュー全体の厳密な保証は別課題です。
- サーバージャッジの完全隔離は保留中で、このコンテスト機能で隔離・課金設定は変更しません。
